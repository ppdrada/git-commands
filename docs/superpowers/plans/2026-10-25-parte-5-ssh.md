# git-commands — Parte 5: chaves SSH e pontos menores — Plano de construção

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** levar o `git-commands` à versão 1.1.0: chave SSH do GitHub configurada com segurança e com confirmação a cada passo, busca em segundo plano que continua sem senha para projetos em SSH, e os pontos menores da revisão da 1.0.0 que a pessoa sentiria.

**Architecture:** o que precisa ser exato fica no executável (`lib/ssh.sh`, subcomando `git-commands ssh`, e ajustes em `common.sh`, `updates.sh`, `secrets.sh`, `guard.sh`, `schedule.sh` e `doctor.sh`), com testes. O jeito de conversar fica na skill nova `chave-ssh` e em ajustes de texto em `regras.md`, `atualizar`, `configurar` e no README. A pessoa digita a senha da chave só no terminal dela; o Claude nunca vê a senha nem a parte privada.

**Tech Stack:** bash (compatível com 3.2), git ≥ 2.28, GitHub CLI (`gh`), OpenSSH (`ssh`, `ssh-keygen`, `ssh-add`), plugins do Claude Code, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-10-25-parte-5-ssh-e-painel-design.md` (seções 3, 4 e 6; a seção 5, o painel, é a Parte 6 e tem plano próprio). O design original (`2026-10-25-git-commands-design.md`) continua valendo.

## Global Constraints

- Bash compatível com 3.2: sem arrays associativos, `mapfile`, `${x,,}`, `;&`; regex com `[[ $x =~ $re ]]` e a regex numa variável. **Sem `case` dentro de `$(...)`** (o bash 3.2 não carrega o arquivo).
- Hooks e executor agendado sem heredoc. O `hooks/run-hook.cmd` só com ASCII (o `cmd.exe` em UTF-8 se perde com acentos).
- Dependências: bash, git, gh, utilitários POSIX e, só na parte SSH, `ssh`, `ssh-keygen` e `ssh-add`. Nada de jq, python ou node. Limite de tempo via `gc_run_with_timeout`.
- Estado em `${GIT_COMMANDS_HOME:-$HOME/.git-commands}`. Em `~/.ssh`, o plugin só escreve o bloco marcado do `config` e linhas do `known_hosts`, sempre pelo `git-commands ssh`. **Nunca lê, mostra ou copia a parte privada da chave, e nunca recebe, digita ou guarda a senha dela.**
- Rede só em `updates scan` (sem `--no-fetch`), `updates pull`, `updates detail`, no hook `pre-edit`, no executor agendado e, a pedido da pessoa, em `ssh test` e `ssh known-hosts`. Sempre sem perguntas (`gc_quiet_net`) e com limite de tempo.
- Nunca existe `git pull` automático; atualizar só por `git-commands updates pull`, a pedido da pessoa.
- Textos para a pessoa em pt-BR simples; ids de conceitos e subcomandos em ASCII kebab-case.
- Fim de linha LF; executáveis com modo 100755.
- Mensagens de commit em pt-BR, no imperativo, terminando com `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Branch `parte-5-ssh`. **Nada vai para o GitHub sem o Dev mandar** (envio, PR, junção, marca de versão).
- Documentação pública sem nomes de pessoas nem de projetos pessoais ("Dev", "projeto").

## Review Focus

1. **Só existe uma chave RSA ou ECDSA antiga** (`~/.ssh/id_rsa`, sem ed25519): o esperado é o plugin usar essa chave em tudo (config, teste, cadastro), sem criar outra. Teste: `test_ssh_usa_a_chave_que_existe` (Task 8).
2. **Pasta do usuário com espaço ou apóstrofo** (`C:\Users\Ana Maria`, `D'Avila`): o esperado é o agendamento e o `~/.ssh/config` funcionarem. Testes: `test_schedule_windows_apostrofo` (Task 6) e o `IdentityFile` sempre escrito como `~/.ssh/<nome>` em `test_ssh_config_escreve_bloco` (Task 8).
3. **Projeto com origin SSH pela porta 443** (`ssh://git@ssh.github.com:443/dono/repo.git`): o esperado é ser reconhecido como GitHub e buscado por HTTPS no segundo plano. Teste: `test_github_ssh_to_https` (Task 2).
4. **`known_hosts` que já tem as chaves do GitHub** (inclusive escritas à mão): o esperado é não duplicar nada. Teste: `test_ssh_known_hosts_grava_uma_vez` (Task 8).
5. **Git configurado com o OpenSSH do Windows** (`core.sshCommand`): o esperado é o `ssh test` e o `ssh status` usarem o mesmo ssh que o git. Teste: `test_ssh_usa_o_ssh_do_git` (Task 8).
